## 反省と気づき

1. **完了済みの背景作業を「待機ループ」で待ち続け、ユーザーに指摘されるまで気づかなかった。**
   `until ! pgrep -f "tmp/076/mutate.sh" >/dev/null; do sleep; done` の**条件文字列自体が
   待機コマンドの command line に入るため `pgrep -f` が自分自身にマッチ**し、対象がとうに
   終わっていても永久に待った。実害は待機に費やしたターン (十数回) と、ユーザーの
   「スタックしていませんか？」1 往復。
   → これは `verify-execution-not-just-exit-code.md` が既に
   「**`pgrep` の存在確認で待たない**。`-f` は command line 全体を見るため、パターンが
   待機コマンド自身の command line に現れると自分にマッチする」と書いている罠そのもので、
   **ルールを読んでいたのに踏んだ**。
   → 切り出し先: 同ルールの当該項に「`until` ループの**条件式に書いた文字列**が自分にマッチする」
   という発動点を 1 行足す案 (今の本文は `pgrep -f` を「使わない」としか書いておらず、
   `until` の条件に書く形が同じ罠だと結びつかなかった)。**要否はユーザー判断**
   → 対策として実際に効いたのは「**待つ対象は成果物ファイルの存在にする**」
   (`until [ -f .../runs.tsv ]`)。これは同ルールの「成果物で判定する」と一致する

2. **codex の max effort フェーズが長く (20〜40 分 × 6 回)、待機のためのターンを大量に消費した。**
   有効だったのは「待ち時間に issue のドラフトを tmp へ書く」「自分でできる裏取り (grep / 計数) を
   先に済ませる」で、実際 087 の「25 行が一字一句同一」は待機中に自分で測った。
   → 切り出し先: `codex-drive` skill に「並列 codex を起動したら、**待機中に main agent がやる
   作業を起動と同時に決める**」を 1 行足す案。**要否はユーザー判断**

3. **「CI でしか出ない不具合」を、新しい CI run を取らずにアーカイブログだけで確定できた。**
   issue 080 は「着手する場合の最小の一歩 = CI で `SMBEE_TRACE_WIRE=1` + gate を立てて 1 run」と
   書いていたが、実際には `gh run view --log-failed` / `--log` で 4 run 分を取れば
   ① 失敗テストの全数 ② 実時間ギャップ ③ Samba 側ログ まで揃い、**issue の前提 3 点の誤りまで**分かった。
   → 気づき: **issue が「新しい観測を取れ」と書いていても、先に既存の失敗 run のログを全部取る。**
   GHA の log retention は 90 日ある。
   → 切り出し先: `instrument-before-second-fix.md` の
   「観測を足す前に、その経路の**既存の観測**を grep する」の CI 版として
   「CI-only の不具合は、新 run を取る前にアーカイブ run のログを全部取る (retention 内なら)」を
   1 行足す案。**要否はユーザー判断**

4. **調査 issue の断定が強すぎ、codex の反証で 10 件弱めた。**
   「Samba は接続を切っていない」(実際は debuglevel 3 で 2 種類のログが無かっただけ)、
   「12.4 秒 = 5 秒 cleanup deadline」(実際は 12 秒台で閉じうる経路が 10 本以上ある) など。
   全件採用して「確定 / 最有力 / 未確定」に書き直した。
   → 気づき: **調査 issue は最初からこの三分で書く**と、後から弱める往復が減る。
   → 切り出し先: **却下** (「主張は証拠ではない」で足りる。今回はレビューが機能して commit 前に直った)

5. **敵対レビューが「新規ファイルが untracked」を P1 で拾った。**
   コードの欠陥ではないが、`test/e2e/container-init.sh` を commit に含め忘れると
   **5 workflow + ローカル smoke の全 launcher が停止する**。実際には含めたが、
   「新規ファイルを作る変更では commit 漏れが単一障害点になる」という攻め口は自分では立てていなかった。
   → 切り出し先: `codex-drive` skill の lens 例に「**新規ファイルを追加する変更では
   『その新規ファイルが commit / checkout に無い場合』を攻め口に入れる**」を 1 行足す案。
   **要否はユーザー判断**

6. **レビュワーの計数を採用せず自分で数え直したのが正解だった。**
   codex は重複ブロックを「31 physical / 29 nonblank / 25 non-comment」と報告したが、
   自分が引用している範囲 (`:43-67`) を数えると 25/24/20 で、レビュワーは別範囲を数えていた。
   issue と commit message には自分の実測値を書き、食い違いも明記した。
   → **却下** (「主張は証拠ではない」どおり。ルールが機能した例として記録するだけ)

7. **issue の「不在の主張」を着手前に数え直したのが決定的だった。**
   「512 KiB × 3 本の 3 テストは安定して green」は誤りで、実際は同 run で 2 本が落ちていた。
   これを鵜呑みにしていたら「multi-flight テスト固有の問題」という誤った枠のまま調査していた。
   → **却下** (CLAUDE.md「issue の『不在の主張』は着手前に数え直す」どおり。守れた例)
