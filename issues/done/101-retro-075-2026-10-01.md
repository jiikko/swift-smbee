# 101 (retro): issue 075（Linux の AES-CCM 高速化）の振り返り

起票日: 2026-10-01

## 概要

issue 075 を codex-drive で進めた（設計 4 案 → 設計レビュー 2 本 → codex 実装 → 実装レビュー 3 lens → 変異 6 本 → fix-ab）。
結果は実転送 64 MiB read 15.1 → 136.3 MiB/s。以下は踏んだところと、他の作業にも効きそうな改善案。

## 項目

経緯の出典はこのセッションの記録（`tmp/075/` の各 log。git 履歴に残るのは実装 commit と後続の末尾カンマ修正だけ）。

### 1. 「独立な oracle」として、production の処理の写しが足された

codex の実装は、テストの答え合わせ役として pure-Swift の CCM の整形処理（B_0・AAD の長さ符号化・padding）を production に
もう 1 組足していた（テストからしか呼ばれない約 100 行）。既存の処理の写しなので、整形の誤りを共有していても気づけず、独立していない。
外部実装（pyca/cryptography = OpenSSL）で固定値を作り、写しは消した（`AESCCM.sealFallback` は本物の fallback を呼ぶ）。
macOS の CommonCrypto 経路が外部の固定値と一致したことで、整形が正しいことの証拠も得られた。

- 一般形: **差分テストの答え合わせ役は「別の実装」で用意する（別ライブラリ・別言語・公開 vector）。同じ repo の同じ処理の写しは独立ではない**
- 切り出し先（提案）: 既存 rule `mutation-verify-new-tests.md` の「実装の二重化・配線」節の既存項「同じ判定・同じ結論を 2 箇所で別実装していないか」に、
  例として「テストの答え合わせ役に足した写しもこれに当たる。oracle は別実装で用意する」を 1 行足す。実行はユーザー判断

### 2. 最後の編集の後に CI と同じ lint を回していなかった

`make lint-analyze`（analyzer rules）は回したが、その後にテストの配列へ固定値を 1 行足し、CI の `SwiftLint (strict)` が trailing comma で落ちた。
analyze と strict lint は別の検査で、手元で回したのは前者だけだった。

- 一般形: **最後の編集の後に、その変更に関係する検査（その種類のファイルを見る lint・テスト）を回し直す**。途中で回した検査の緑は、その後の編集を検査していない
- 切り出し先（提案）: 既存 rule `verify-execution-not-just-exit-code.md` に上の一般形を 1 行追記。この repo 固有には、
  CLAUDE.md の smoke の節に strict lint のコマンドを並べる案もある（局所）。実行はユーザー判断

### 3. 計測ハーネスの環境の前提が 2 回外れた

Linux container（`swift:6.2` image）で、(a) `python3` が無く変異を当てられない、(b) `swift build -c release --build-tests` では testable にならず
テストが走らない、で 2 回空振りした。どちらも「全部失敗」として出たので誤判定はしなかったが、往復が 2 回増えた。
(b) は 097 でも踏んでいる。

- 一般形: 局所的（この image とこの SwiftPM の挙動）。直し方: 変異ファイルは host で作って container ではコピーだけにする / release のテストは
  `swift test -c release --filter <対象>` でビルドする（release の全 suite 実行は 075 のとおり不可）。この issue に書いたことで決着（rule 化しない）
