# 100 retro: issue 098 / 091 / 097（guest job の復旧・prewarm 分岐の検査・実 Samba 転送の分解測定）

起票日: 2026-09-30

## 概要

1 セッションで 098（SMB 3.0.x が暗号化非対応の server にも TRANSFORM を送っていた bug）、091（resource performance の
payload を実行で検査する）、097（実 Samba 転送の律速の分解測定）を片付け、097 から 099（frame header の別 send による
往復待ち）を起票した。以下は踏んだところと、次に効きそうな改善。

## 項目

### 1. 古い commit と A/B を組む前に、測りたい経路がその commit で実際に動くかを確かめる

- どこで: 097 の手順 5（060 の CMAC 改善を `e91809a^` / `e91809a` で A/B）。098 より前の SMBee は SMB 3.0.x で常に暗号化して
  いたので、060 の CMAC 署名は実 Samba の転送では一度も wire に乗っていなかった。issue の計画は「古い commit に HEAD の
  harness を載せれば比べられる」前提で書かれていて、計画の段階では誰も気づかなかった（codex の設計リードが「古い commit では
  切断されうる」と指摘し、backport を載せる代替 A/B にした）
- 一般形: **過去の commit と性能・挙動を比べる計画を立てるときは、比べたい経路がその commit で到達可能かを、後から入った bug fix や
  前提の変化も含めて先に確かめる**。到達しないなら、その A/B は「効果がゼロ」ではなく「測れない」
- 切り出し先（提案）: `~/dotfiles/_claude/rules/perf-claims-need-measurement.md` の「過去の実測値が再現しないときは…」節への追記
  （発動点は同じ「過去の commit と比べるとき」。新規 rule にはしない）

### 2. copy を減らす perf 変更が、別の系で latency を大きく悪くしていた

- どこで: `0709833 perf(transport): send direct TCP frames as segments` は payload の copy を 1 本減らしたが、frame header を
  別の `send()` にしたため、Linux の実 socket では往復ごとに Nagle と遅延 ACK の待ちが乗った（1 MiB read 168 ms、TCP_NODELAY で
  5.8 ms）。in-memory の性能テストと macOS の手元（遅延 ACK の挙動が違う）では見えず、2 か月気づかれなかった
- 一般形: **perf の変更を「速くなった」と判断した測定系（in-memory / 手元の OS）と、本番の系（実 socket / 本番の OS）で
  律速が違いうるときは、本番の系で 1 回 A/B を取ってから採る**。throughput の benchmark は latency の退行を見ない
- 切り出し先（提案）: `perf-claims-need-measurement.md` の「測った経路がユーザーの実経路と同じかを…確かめる」項への追記
  （同じ発動点の具体例。新規 rule にはしない）

### 3. dotfiles の `bin/mutate-verify` がこの repo では動かなかった

- どこで: 098 の変異検証。`mutate-verify` は dotfiles の `scripts/lib/worktree_scratch.sh` を repo 相対で読むので、
  他の repo では変異を当てる前に rc=2 で止まる。global rule（`mutation-verify-new-tests.md`）は「手で組む前に
  `bin/mutate-verify` を見る」と全 repo 向けに書いている
- 一般形: **global rule が推す道具は、推す範囲（全 repo）で動くか、動かない範囲を rule に書く**
- 切り出し先（提案）: dotfiles の新規 issue（`mutate-verify` を他 repo でも動くようにするか、rule に「dotfiles 内のみ」と書く）

### 4. 局所的な出来事（提案にしない）

- debug trace が署名・暗号化**前**の bytes を「TREE_CONNECT request」と名乗って出していたため、098 の調査で自分と codex の両方が
  「未署名で送っている」と一度読み違えた。この repo の `debugDump` の置き場所の問題で、観測点を副作用の後に置く規律は
  `mutation-verify-new-tests.md` に既にある。直すなら 099 の実装時に送信直前の trace を足す
- `gh run watch` が run の途中で rc=0 のまま抜けた。待つ対象を成果物（status=completed）にする規律は
  `verify-execution-not-just-exit-code.md` に既にある。その場で poll に切り替えた
- `swift build -c release --build-tests` は testability を有効にしないので `@testable import` の harness が release で通らない。
  この repo の道具の中で直した（`network-performance-study-run` のコメント）
