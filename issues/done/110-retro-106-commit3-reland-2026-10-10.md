# 110 (retro): issue 106 Commit 3 の入れ直し（性能の退行の原因究明と、実装後の敵対レビュー 5 周）の振り返り

起票日: 2026-10-10

## どこで踏んだか

1. **性能の退行の原因を、命令数でも context switch の数でも直接は削れなかった。**
   callgrind の命令数（arm64 container）は +4.9% だけで、x86 の user CPU +39% を説明できなかった。voluntary context switch は x86 の CI のログで +94%、
   arm64 container の read_stream の単独実行で約 300 倍（約 560 → 約 177,000）に増えていたが、
   それを減らす変更（reader の起動位置・transport の executor・inline の送信）は、どれも throughput を大きく落とした。
   効いたのは「session の仕事を担う Task を 1 つの直列 executor に集める」という構造の変更（E6）で、これは
   境界を 1 つずつ削る実験からは出てこず、前提（スレッドに散ること）を変える仮説から出た。
2. **計測の物差しの作り直しに時間を使った。** CI の性能 gate は master への push でしか比較の相手を用意せず、branch の候補を測れなかった。
   `reference_sha` を足したら、同じ commit に手動起動の run が並び、verifier がそれを掴んで落ちた。
   master の ref で手動起動したら concurrency で push の run が取り消された。
3. **実装後の敵対レビューが 5 周続いた。** 毎周、前の周の修正に新しい穴が見つかった。cleanup の FileId の台帳は 2・3・4 周目に続けて破られた。
   2 周続いた時点（3 周目の修正）で遷移を 1 関数に寄せて遷移表で固定したが、4 周目に「試行の識別子が無い」穴が出て、所有者を持たせてやっと収束した。
   関数に寄せるだけでは足りず、「誰の記録か」を状態に持たせる必要があった
4. **検閲と指示の誤り。** progress の二重通知の修正で、レビューの提案（stream 側に `onProgress: nil` を渡す）をそのまま採り、既知のサイズと速度を落とした
   （提案の採用と検閲の誤り）。その次の周で、エラー時に後始末の前に progress を待つ順序を codex への指示に書いた（指示の誤り）。
   テストが 1 件落ちているのに `;` で commit まで進めた
5. **テストの不安定さの多くは「待つ合図が、assert する事象と違う」形だった。** `.background` の Task（macOS で 3 秒以内に走らない）、
   到着順の前提（2 つの Task の列への入る順）、件数の waiter に通知しない helper、transfer の停止を「cancel の適用」の代わりに待つ。
6. **codex が制約を自分に向けて読み違えた。** 「container は同時に 1 台」を、他人の container（monolink）が動いているので守れないと読み、Linux の確認を飛ばした。

## 次に効きそうな改善（一般形）

- A. **性能の退行は、主要な指標（throughput・CPU）の差を、仮説ごとの内訳（命令数・待ちと起床など）で説明できるかを先に確かめる。
  内訳の代理の指標（context switch の数など）を減らしても主要な指標が良くなるとは限らないので、代理の指標の減少だけで改善と判断しない。**
  - 切り出し先の提案: 既存ルール `perf-claims-need-measurement.md` へ追記する
- B. **CI の検査を手動起動で回せるように入力を足したら、同じ commit に push 以外の run が並ぶことを前提に、その run を読む側（verifier・集計）を同じ変更で直す。
  手動起動の前に、検証の対象の run と concurrency group が衝突しないか（取り消し合わないか）を workflow の設定で確かめる。**
  - 切り出し先の提案: 既存ルール `verify-execution-not-just-exit-code.md` の「起動しなかった / 取り消された run は、その commit を検証していない」節へ追記する
- C. **サブエージェントへの資源の制約（同時に何台・何本）は、数える範囲（自分が起こすもの / チーム / マシン全体）と、上限に当たったときの扱い（待つ・縮小する・報告する）を書く。**
  範囲が無いと、他人の資源を数えて工程を黙って飛ばす
  - 切り出し先の提案: 既存ルール `subagent-model-tiering.md` の「指示を書くとき」へ追記する（禁止制約と正道の衝突の項の隣）
  - 追加の実例（2026-10-12、2 回目）: CI でだけ落ちたテストの調査で、codex が「container は同時に 1 台まで」を、既に動いている他人の container（monolink）を数えて
    守れないと読み、Linux の検証を飛ばした（main agent が自分で回して補った）。同じ日に、指示に無い CI の job（macOS runner の `resource-lifecycle`）を workflow に足した
    （main agent が戻した）。どちらも「数える範囲」「足してよいものの範囲」を書かなかった指示の側の穴
- D. **状態の台帳（誰かが書き、別の経路が後から読む・上書きする表）を 1 関数に寄せるときは、各記録に「その記録を作った試行の所有者」を持たせ、所有者が一致する遷移だけを許す形まで一度に作る。**
  関数に寄せるだけでは、遅れて届く別の試行の遷移を区別できない。
  - 切り出し先の提案: 既存ルール `adversarial-review-own-safeguards.md` §7 の「同じ判定の別々の書き方…1 つの関数へ寄せる」の項へ追記する（関数に寄せる部分は既存。所有者の部分が差分）
